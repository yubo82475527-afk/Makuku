# 数据设计原则

## 设计目标

数据模型应同时支持业务执行、异常追踪、经营分析和历史复盘。不得只根据单个页面的展示需求临时设计数据结构。

## 数据分层

### 事实数据

事实数据记录真实发生的业务事件或业务状态，例如价格采集、门店拜访、促销活动和销售结果。

事实数据应明确：

- 业务对象和数据粒度
- 事件发生时间与入库时间
- 数据来源、来源标识和采集方式
- 原始值、标准化值和处理状态
- 更正、重跑或重复数据的处理规则

### 维度数据

维度数据描述相对稳定的经营对象，例如区域、人员、门店、渠道、产品、SKU、竞品和经销商。

维度设计应支持组织关系和业务属性随时间变化。需要历史口径时，应保留有效期或版本，而不是直接覆盖旧值。

### 聚合与分析数据

聚合数据服务于稳定且高频的经营分析，例如目标达成、价格异常、执行进度和趋势变化。

新增聚合表前必须明确：

- 来源事实和计算口径
- 聚合粒度与刷新频率
- 迟到数据和重算策略
- 数据质量和样本充分性
- 由哪个领域负责维护

可以由现有事实或聚合稳定计算的指标，不应仅为某个页面重复落表。

## 粒度与职责

每张表必须有唯一、清晰的业务粒度和职责。设计评审时应能用一句话说明“一行代表什么”。

禁止让同一张表同时承担不同粒度的职责。例如，城市-渠道-SKU 的每日价格上下文不应同时承载门店级异常和人员执行跟踪。

跨层数据流应保持单向和可解释：原始事实 → 业务聚合 → 治理信号 → 智能结果 → 经营动作。下游结果不得反向覆盖原始事实。

## 历史与可追溯性

- 重要业务状态应保留变化历史或可重建历史
- 规则、模型和上下文应有版本标识
- AI 结果应记录输入依据、生成版本和审核状态
- 人工修正应记录修改人、时间、原因和修改前后值
- 指标口径变化必须可识别，避免不同版本结果被直接比较

## 数据质量

数据质量不应只用“有或没有”判断。分析结果应根据业务需要考虑有效样本数、覆盖范围、时效性、来源可靠性和异常值。

质量控制指标主要用于判断结论是否可信。除非它本身是经营目标，否则不应直接成为管理者首页的核心业绩指标。

## 当前数据库实现

当前数据库使用 Supabase PostgreSQL，通过 `supabase/migrations/` 中按时间递增的 SQL 迁移演进。迁移中已经包含表、索引、RLS、Policy、触发器和 RPC。应用同时存在对旧字段或未完成迁移环境的兼容回退，因此设计文档必须区分目标结构与当前已部署结构。

价格领域的 Raw Fact、Business Aggregation、Governance、Intelligence 和 Agent 是业务职责分层，不表示数据库必须拆成五个物理 Schema，也不表示所有目标表都已落地。

## 迁移规则

- 所有 Schema 变化必须新增迁移文件，不得修改已应用迁移来改写历史
- 迁移文件名沿用时间序号和清晰业务名称，并保持可重复部署
- 新增表或关键字段时，同时评估唯一键、外键、索引、默认值、非空约束和历史数据回填
- 对线上已有数据的变更，应明确兼容窗口、回填方法和移除旧逻辑的条件
- 破坏性删除、重命名或类型修改必须分阶段实施，不得在同一次发布中直接切断旧读写路径
- 数据修复脚本与 Schema 迁移分开；脚本必须支持幂等、统计处理结果并可安全重跑
- 新迁移必须检查 `git diff`，避免夹带数据库导出、环境配置或无关格式变化

## 权限与访问边界

- 新表必须明确是否启用 RLS，并为实际访问角色设计最小权限 Policy
- `SUPABASE_SERVICE_ROLE_KEY` 只能在服务端使用，不得进入 Client Component、浏览器包、公开响应或日志
- 使用 Service Role 的 API 必须先完成应用层鉴权，不能把 RLS 绕过能力当作默认授权
- 面向用户的 Route 应使用统一 Session/角色检查；定时任务和内部任务应验证专用 Secret
- 不得仅因路径位于 `/api/internal` 就认为接口已经受保护
- Anon Client 与 Service Client 的选择必须基于访问主体和权限需要，不得为了查询方便默认使用 Service Role

## RPC、触发器与应用逻辑

以下场景可以使用数据库 RPC 或触发器：

- 需要事务保证的多表写入
- 高并发下必须原子领取、去重或更新的任务
- 多个入口必须共享且不能绕过的数据不变量
- 批量导入中需要在数据库侧保证幂等和性能的操作

以下逻辑优先放在领域服务中：

- 经常变化的业务流程编排
- 需要调用外部服务或 AI 的逻辑
- 页面专属格式化和展示规则
- 需要清晰单元测试的复杂经营判断

数据库函数和触发器必须有明确输入、输出、错误语义和对应测试，不得隐藏难以追踪的跨领域副作用。

## Demo 与兼容回退

当前部分读取逻辑在缺少 Supabase 配置、表结构缺失或查询失败时返回 Demo 数据。新增功能不得默认复制这种模式。

- Demo fallback 必须显式返回 `isDemo` 或等价状态，页面不得把模拟数据伪装成真实经营结果
- 生产环境的权限错误、数据错误和配置错误不得静默降级为 Demo 数据
- 兼容旧字段的回退应记录移除条件，不能永久叠加新的 legacy 分支
- 新领域是否需要 Demo 数据必须由产品用途决定，而不是作为异常处理的通用方案

## 建模检查清单

- 是否明确了表的业务粒度和唯一键？
- 是否已有表可以承担该职责？
- 是否区分原始事实、业务状态和计算结果？
- 是否支持历史追踪、幂等处理和重算？
- 是否记录来源、版本和审计信息？
- 是否会与其他表形成职责重叠或口径冲突？
- 是否确实属于当前版本范围？
- 是否通过增量迁移、RLS 和正确的服务端权限实现？
- 是否需要兼容旧结构，兼容逻辑何时移除？
- 是否有幂等、回填、重算和失败恢复方案？
