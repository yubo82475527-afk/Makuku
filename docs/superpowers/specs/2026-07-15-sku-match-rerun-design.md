# SKU 匹配重构与手动重跑设计

## 目标与边界

用销售提供的 327 条竞品档案替换当前有效竞品池，并建立稳定、可解释、便于小改的纯硬规则匹配。管理员可在现有巡店分析监控中按日期或单个 Visit 手动重跑匹配。重跑读取已保存的图片解析结果，不再调用图片 AI，但后续候选替换、审核和价格快照流程与现有单 Visit 重跑一致。

不新增页面、不在移动 H5 增加操作、不建设新的通用规则引擎或任务平台。

## 解耦结构

匹配分成三层：

1. `product-match-engine.ts`：稳定流程和数据契约。负责索引、候选池、过滤顺序、唯一候选判断和 Match Method，不包含具体品牌/系列别名。
2. `product-match-rules-v2.ts`：当前规则版本。负责别名、Signature 提取、字段兼容和冲突判断。未来小改主要发生在这里及对应测试。
3. 候选与 Visit 服务：通过注入的数据网关负责加载数据、候选生命周期、审核和快照，不理解具体匹配规则；HTTP、鉴权和 Supabase 细节留在路由适配层。

正常 H5 与手动重跑共享同一个匹配上下文和候选构建函数。日期范围重跑只加载一次主数据并复用索引。

## 主数据切换

Excel 的 `piece_count` 已是整数总片数，直接保存。导入先完整预览和校验，再通过单个事务停用旧竞品并批量插入新竞品；任何插入失败都会回滚，不留下空的有效商品池。

旧竞品不删除，历史价格不删除。竞品对标只保留 `competitor_series_mappings`：竞品品牌/系列映射到 Makuku 系列；需要具体物料时，再按目标系列、标准尺码和形态从 `material_master` 确定候选。H5 图片商品匹配只负责识别实际商品主档，不承担竞品到自有 SKU 的持久化映射。

现有 `sku_matches` 单品级关系从页面、API、导入导出和运行时读取中移除。为避免数据库迁移先于应用发布造成旧版本查询失败，本次先停止所有读写；确认线上无消费者后，再用下一次独立迁移删除物理表。

## 匹配规则

输入证据包括 `brand`、`product_family_text`、`section_title`、`sku`、`row_anchor` 和整数 `piece_count`。Signature 包含品牌、系列、包装层级、形态、尺码、总片数和版本。

流程固定为：证据归一化、品牌/系列解析、商品池选择、Signature、索引过滤、唯一候选、绑定。停用商品、重复 Signature、字段冲突和多候选不得自动绑定。

方法只有 `EXACT_CODE`、`FULL_SIGNATURE`、`UNIQUE_SIGNATURE` 和 `UNMATCHED`。`match_score` 仅保留 1/0 兼容值；UI 与应用审核使用方法，不再展示伪概率。

## 手动重跑

巡店分析监控提供日期范围和单 Visit 两种入口，共用一个确认弹窗。请求同步完成匹配重建并返回汇总；既有质量门禁和自动审核继续异步处理后续状态，不新增状态接口、内存任务或任务表。

每个目标 Visit 执行：读取存量 Vision 行、删除目标图片旧快照、旧候选标记为 `rejected + reanalyzed`、创建 v2 候选、刷新 Visit、触发现有审核流程。失败 Visit 返回明确原因，其他 Visit 的结果仍然汇总返回。

弹窗只显示提交中、成功或失败以及最终计数，不模拟无法保证的进度。完成后刷新监控，现有 H5 详情展示新的 SKU、匹配方法和待审核/已审核状态。

## 验收

- 327 条、21 个品牌的新档案原子切换为有效竞品，旧竞品和历史事实仍存在。
- “竞品映射”是唯一对标入口，页面明确为系列级映射，不再出现单品级 Makuku SKU 映射。
- `DRYCARE`、Medium、Large 等规则通过，重复或冲突保持未匹配。
- 改一个别名不需要修改 Visit/API/UI 流程代码。
- 单 Visit 和日期范围重跑均不调用图片 AI，并正确替换候选和快照。
- 监控页有管理员操作，移动 H5 没有新增入口。
- 自动测试、Lint、Build 和 100 SKU 性能检查通过。
