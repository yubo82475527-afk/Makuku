# 组件复用规则

## 目标

组件设计应保持业务表达清晰、交互一致和修改范围可控。复用不是追求最少文件，也不是把所有功能塞进一个可配置巨型组件。

## 当前基础

仓库已有 `src/components/ui.tsx`，提供 `Card`、`MetricCard`、`Badge`、`TextInput`、`SelectInput`、`Button`、`EmptyState` 和 `DataNotice` 等基础组件；同时已有 App Shell、页面状态、搜索选择器、导入工作台和业务表格等共享实现。

部分门店拜访和价格审核组件已经较大。新增功能触及这些组件时，应优先拆出本次能够独立命名、测试和复用的职责，不得继续无边界堆积，也不要求一次性重写整个组件。

## 组件层级

### 基础 UI 组件

位置优先为 `src/components/ui.tsx`；当数量或职责明显增长时，可以迁移到 `src/components/ui/`。

基础 UI 只表达视觉和通用交互，例如按钮、输入框、徽标、空状态和加载状态，不包含价格、门店、组织等领域规则。

### 共享领域组件

服务同一领域的多个页面或流程，例如产品选择、价格证据、门店选择和导出任务状态。组件名称和 Props 应使用业务语言，并封装稳定领域交互。

共享领域组件不能通过大量布尔参数支持彼此无关的流程。差异较大时，复用较小的子组件或领域 Hook，而不是制造万能组件。

### 页面专属组件

只服务单个路由的布局和编排。页面专属组件可以组合基础 UI 和领域组件，但不应被其他页面通过深层相对路径依赖。

只有出现第二个真实使用方，并且业务语义一致时，才将页面专属逻辑提升为共享组件。

## 新建前检查

新建组件前必须：

1. 使用文件搜索和文本搜索检查现有组件、相似交互与样式。
2. 判断现有组件能否直接复用，或通过不破坏职责的小幅扩展复用。
3. 确认新组件属于基础 UI、共享领域还是页面专属层级。
4. 明确状态由 Server、页面容器还是组件自身负责。
5. 确认权限、国际化、加载、空数据、错误和移动端状态由谁处理。

不得复制现有组件后只修改名称、文案或少量样式。发现近似组件时，应先统一稳定公共部分。

## 何时复用与抽象

适合复用：

- 业务语义相同，仅数据或文案不同
- 交互状态机一致
- 修复缺陷时多个使用方应该同时获得修复
- Props 可以用清晰业务概念表达

不适合强行复用：

- 只有视觉相似，业务规则和权限不同
- 需要大量布尔参数、条件分支或插槽才能兼容
- 两个流程预计会独立演进
- 抽象后调用方比原实现更难理解

出现少量重复时先保持局部清晰；当重复稳定、已有两个以上真实使用方并且变化原因相同时，再提取抽象。

## 拆分大型组件

行数不是唯一标准。出现以下信号时应拆分：

- 同时负责数据请求、业务计算、表单状态、弹窗、列表和明细展示
- 一个修改经常影响多个不相关流程
- Effect 和状态之间存在难以解释的耦合
- 相同逻辑已被其他页面复制
- 关键业务逻辑无法在不渲染整个页面的情况下测试

推荐按职责拆分：

- 纯业务计算移到 `src/lib/<domain>.ts`
- 数据请求和异步状态集中在页面容器或领域 Hook
- 大型表单拆成有独立业务含义的区块
- 弹窗、菜单、筛选器和任务状态成为独立组件
- 纯展示组件接收已整理好的 View Model，不直接读取数据库结构

拆分不得改变用户流程、权限或数据口径。每次只处理当前需求触及的职责，并补充相应测试。

## 状态与数据边界

- 可由服务端确定的初始数据和权限优先在 Server Component 处理
- 浏览器交互状态保留在最接近使用位置，不为避免 Props 而随意增加全局 Context
- URL 可表达的筛选、分页和当前视图应优先保留在 URL，支持刷新和分享
- 不在多个组件中维护同一份可变业务事实
- 服务端响应先转换为页面需要的类型，避免组件深度依赖 Supabase 联表返回结构
- 写操作必须提供进行中、成功、失败和重复提交保护

## 统一交互模式

- 优先使用已有基础 UI，新增变体应扩展稳定语义，不在页面反复拼接相同类名
- 图标使用现有 `lucide-react`，不要重复手绘通用图标
- 表格必须考虑加载、空数据、错误、分页、窄屏和长文本
- 筛选条件应可清除，并保持标签、URL 参数和 API 参数语义一致
- 弹窗必须有明确标题、取消路径、提交状态和错误反馈
- 权限不仅控制可见性，还必须由服务端再次校验
- 中英文文案进入现有 i18n 机制，不在组件中建立新的字典模式

## 列表筛选标准（冻结）

列表页筛选以「需人工审核」(`offline-price-candidates`) 为唯一标准样式。新建或改版筛选时直接对齐该实现，不要另起一套更宽、多行标签或独立卡片式筛选。

标准参考：`src/app/[locale]/offline-price-candidates/page.tsx` 中的 `QueryForm` 与局部筛选字段。

必须遵守：

1. 使用 `QueryForm` + `QuerySubmitButton`（`src/components/query-form.tsx`），筛选条件写入 URL。
2. 外层网格：`grid gap-3`，按字段数量选择列数（如 `md:grid-cols-2 xl:grid-cols-3`）。**一行放不下就换行**，不要强塞进单行导致重叠或按钮被压扁。字段少时可参考需人工审核用 `xl:grid-cols-[minmax(280px,1fr)_…]` 封顶；字段多时优先 2–3 列自动换行。
3. 字段外观统一为单行内联：`flex min-h-10 items-center rounded-md border border-slate-300 bg-white px-3 text-sm ... focus-within:border-slate-500 focus-within:ring-2 focus-within:ring-slate-200`。
4. 文本/下拉：左侧短标签 `text-xs font-medium text-slate-500`，右侧 `min-w-0 flex-1` 控件。
5. 日期范围：不在字段内再放可见标题，只用 `aria-label`；两个 `type="date"` 用 `min-w-0 flex-1`，中间分隔「至」/「to」。不要给日期输入加过大的 `min-w-*` 或 `col-span` 撑宽。
6. 操作区只放「筛选」（及可选「重置」），与字段同网格对齐；换行后留在下一行左侧即可，不要为占满宽行而拉伸按钮。

## Props 与类型

- Props 使用业务含义明确的名称，避免 `data: any`、`mode2` 或含义不清的布尔组合
- 优先传递组件真正需要的 View Model，不传递整个数据库记录作为便利接口
- 回调名称表达业务事件，例如 `onApproveCandidate`，而不是模糊的 `onAction`
- 共享类型放在所属领域模块；只有跨多个领域稳定共享时才进入全局类型文件
- 不为单次调用创建复杂配置 DSL

## 验证要求

组件修改后按风险选择验证：

- 领域计算和状态转换使用自动化测试
- 关键页面结构和架构边界可使用现有 Node Test
- 交互流程、响应式布局和视觉问题使用 Playwright 浏览器验证
- 至少检查加载、空数据、错误、成功和权限受限状态中与改动相关的部分
- 涉及移动端 H5 时必须验证实际窄屏视口和触控流程

## 评审清单

- 是否搜索并评估了现有实现？
- 组件属于哪个层级，职责能否一句话说明？
- 是真实复用还是仅视觉相似？
- 是否引入了过多参数或条件分支？
- 数据、权限和异步状态的所有者是否清晰？
- 是否继续扩大了已有巨型组件或全局共享文件？
- 是否覆盖了加载、错误、空状态、移动端和国际化？
- 测试是否与行为风险相匹配？
